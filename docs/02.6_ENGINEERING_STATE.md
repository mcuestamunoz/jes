# JES — Engineering State

> This document defines the Engineering State contract: the live representation of an engineering cycle in progress.  
> It is not Engineering Cognition. Cognition defines meaning.  
> Engineering State defines the executable instance of that meaning during a cycle.

---

## What Engineering State is

**Engineering State** is the explicit object that represents the current engineering cycle.

It answers, at any moment:

> What are we doing, which intention are we in, what is still open, and what is allowed?

It carries both:

- operational facts of execution,
- cognitive position of the cycle (`current_mode`).

It does not redefine Modes, Principles, Workflow, or Operations.

---

## Design principle

> **State stores execution facts. Core stores knowledge.**

If a value can be derived from `current_mode` and Engineering Cognition, it must not be duplicated in state.

Examples of derived (non-state) data:

- mode artifact,
- mode non-goals,
- mode intention,
- mode characteristic question.

## Fields

### Cycle identity

| Field | Type | Meaning |
|---|---|---|
| `cycle_intent` | text | Objective of the engineering cycle |
| `scope` | text / bounds | What may change |
| `execution_status` | enum | `idle` \| `interpreting` \| `active` \| `blocked` \| `awaiting_approval` \| `closed` \| `cancelled` |

### Cognitive position

| Field | Type | Meaning |
|---|---|---|
| `current_mode` | enum | Current Mode (Explore…Evolve) |
| `movement_trigger` | object \| null | Why the last mode transition happened |

`movement_trigger` shape:

```text
movement_trigger:
  type: evidence | decision | constraint | objective | clarification
  reason: text (optional)
```

### Operational context

| Field | Type | Meaning |
|---|---|---|
| `relevant_workflow_phases` | list | Workflow phases implicated |
| `applicable_rules` | list | Active rules |
| `required_artifacts` | list | Expected closure artifact bundle |
| `open_questions` | list | Unresolved ambiguities |
| `active_operation` | enum \| null | Operation currently in progress |

### Governance (conditional)

| Field | Type | Meaning |
|---|---|---|
| `authority_gates` | list | Decisions requiring Engineer approval |
| `coherence_checklist` | list \| null | Coherence concerns for code/tests/docs/contracts/workflow |

`coherence_checklist` is present only when relevant:

- Build
- Validate
- Close

In Explore (and similar early modes), it should be `null` to avoid noise.

---

## Invariants

1. Exactly one `current_mode` at a time.
2. `current_mode` must be coherent with `active_operation` when `active_operation` is not null.
3. Build is blocked while blocking `open_questions` remain, unless the Engineer explicitly accepts a minimum cycle.
4. The Agent never closes Decide autonomously; it proposes and sets `awaiting_approval` when needed.
5. Mode movement requires a typed `movement_trigger`.
6. Governance is not a Mode; it constrains all fields and transitions.
7. Incomplete or contradictory state forces `execution_status = blocked`.
8. `coherence_checklist` is required only for Build / Validate / Close contexts.
9. `execution_status = closed` requires satisfied closure artifacts and Engineer approval when applicable.
10. State must not duplicate static Mode properties defined by Engineering Cognition.

---

## Transition rules

Mode transitions update state; they do not rewrite Cognition.

```text
update_mode(new_mode, trigger):
  require trigger.type in {evidence, decision, constraint, objective, clarification}
  require authority_gates respected
  set current_mode = new_mode
  set movement_trigger = trigger
  require coherence(current_mode, active_operation)
  derive mode views from Engineering Cognition
  if new_mode in {Build, Validate} or closing:
      ensure coherence_checklist is present
  else:
      coherence_checklist = null
```

Movement is evidence-driven.  
Preferred paths may exist, but transitions are not a mandatory pipeline.

## Persistence (summary)

Engineering State is **persistable, not necessarily persisted**.

Creation, restoration, persistence policy, conversation boundaries, and end-of-life behavior are defined in:

- `02.7_ENGINEERING_STATE_LIFECYCLE.md`

## Consumers

| Consumer | Responsibility |
|---|---|
| Interpretation | Creates and updates state |
| Operations | Read `current_mode`, constraints, and `active_operation` |
| Workflow | Uses `required_artifacts` and `execution_status` for progress/closure |
| Engineering Cognition | Resolves derived Mode meaning |
| Integration Operating Model | Implements create/update/persist/consume mechanics |

Operations do not consult Cognition ad hoc for every action.  
They consult Engineering State.  
Cognition remains the source of Mode meaning behind that state.

## Non-goals

This document does not:

- redefine Modes,
- define lifecycle behavior (see `02.7`),
- define prompts or commands,
- specify storage format (file, memory, DB),
- grant decision authority to agents,
- require persistence for every session.

---

## Evolution

Changes to this contract require:

1. explicit Engineer approval,
2. demonstrated need from real cycle execution,
3. no contradiction with Principles or Engineering Cognition.

Field minimization is intentional. Prefer deriving knowledge from Core over growing state.
