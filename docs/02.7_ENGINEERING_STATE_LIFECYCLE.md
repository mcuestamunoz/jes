# JES — Engineering State Lifecycle

> This document defines how Engineering State is born, evolves, persists, and ends.  
> `02.6_ENGINEERING_STATE.md` defines what the state is.  
> This document defines how the state lives during an engineering cycle.

---

## Purpose

Engineering State is not useful as a static schema alone.

Integrations need a shared lifecycle answering:

- When is state created?
- Who initializes it?
- Who may change `current_mode`?
- When does `execution_status` change?
- When is state persisted or restored?
- What happens in a new conversation?
- What happens when a cycle is resumed days later?
- When does state end?

This lifecycle is a Core behavior contract.  
Integrations implement it; they do not invent a private lifecycle model.

## Lifecycle overview

```text
create / restore
      |
      v
 interpreting
      |
      v
   active  ←→  blocked
      |    ←→  awaiting_approval
      v
 closed | cancelled
```

Preferred path is a guide. Real cycles may loop while evidence requires movement.

---

## 1. Creation

Engineering State is created only when a **Cycle Intent** exists.

Creation triggers:
- Engineer states an explicit cycle objective, or
- Engineer resumes an open persisted cycle.

Non-triggers:
- casual questions without Cycle Intent,
- greetings,
- informal exploration with no cycle scope.

No Cycle Intent ⇒ no Engineering State.

---

## 2. Initialization

| Actor | Responsibility |
|---|---|
| Engineer | Provides `cycle_intent` and any known `scope` |
| Integration | Materializes the state object |
| Interpretation | Fills initial fields and selects initial `current_mode` |

### Initial mode selection

Interpretation determines the initial mode from:

- Cycle Intent,
- available repository context,
- explicit prior decisions already approved.

`Explore` is **not** a rigid default.

Examples:

| Cycle Intent | Likely initial mode |
|---|---|
| “Explain how the planner works.” | Explore |
| “Compare these two architectures.” | Design |
| “Implement approved ADR-014 exactly.” | Plan or Build |
| “Review this PR.” | Validate |

If initial mode cannot be determined safely:

- add `open_questions`,
- set `execution_status = blocked` or `awaiting_approval`,
- do not invent direction.

### Typical initial values

```text
cycle_intent        = <from Engineer>
scope               = <explicit or unresolved>
execution_status    = interpreting
current_mode        = <selected by Interpretation>
movement_trigger    = null
active_operation    = null
open_questions      = [...]
required_artifacts  = [...]   # completed during Interpretation
coherence_checklist = null    # unless starting in Build/Validate/Close context
```

---

## 3. Who may change `current_mode`

Mode changes occur only through the state transition contract in `02.6` (`update_mode` + typed `movement_trigger`).

| Actor | Authority |
|---|---|
| Engineer | Always may change mode |
| Integration / Agent | May change mode only with typed trigger and without violating `authority_gates` |
| Operation | May propose movement on completion; does not mutate mode as a side effect outside lifecycle rules |

Requires Engineer approval (`awaiting_approval`) when:

- Decide closes strategic/architectural direction,
- Build is requested while blocking questions remain,
- `scope` expansion is required.

---

## 4. `execution_status` transitions

Allowed statuses:

```text
idle
interpreting
active
blocked
awaiting_approval
closed
cancelled
```

| Transition | When |
|---|---|
| → `interpreting` | Cycle Intent received or restored state being revalidated |
| `interpreting` → `active` | State coherent; mode clear; operation may run |
| `active` → `blocked` | Invariant broken, contradiction, or missing required context |
| `active` → `awaiting_approval` | Authority gate reached |
| `blocked` / `awaiting_approval` → `active` | Clarification or Engineer approval received |
| → `closed` | Closure artifacts satisfied + Engineer approval when applicable |
| → `cancelled` | Engineer abandons the cycle without closure |
| → `idle` | Only for pre-cycle or post-cleanup non-live placeholders; not a substitute for `cancelled` |

`closed` and `cancelled` are terminal for the live cycle.

---

## 5. Persistence

Engineering State is **persistable, not necessarily persisted**.

### Persist when

- cycle spans multiple sessions,
- handoff across tools/agents is required,
- status remains `awaiting_approval`,
- Engineer requests persistence,
- cycle will pause while still open.

### Do not persist when

- no Cycle Intent exists,
- short in-session work that closes immediately,
- ephemeral clarification with no cycle identity.

### Persist / restore rules

- Persist only state fields defined in `02.6`.
- Never persist derived Mode properties as source of truth.
- On restore, rehydrate derived views from `02.5`.
- If restored state is stale or contradictory → `blocked` + `open_questions`.

---

## 6. New conversation

A new conversation does **not** automatically create a new cycle.

> **Cycle identity follows Cycle Intent (and scope), not chat session identity.**

This is a foundational rule of the lifecycle.  
A chat is a transport. A cycle is the unit of engineering work.

```text
Explicit Cycle Intent?
  no  -> no Engineering State (or non-cycle ephemeral assistance)
  yes -> open persisted state exists for this cycle?
           yes -> restore -> interpreting/revalidate -> resume
           no  -> create new state
```

---

## 7. Resume after time gap

```text
restore state
  -> validate invariants
  -> rehydrate derived Mode meaning from Cognition
  -> Engineer confirms cycle_intent/scope still valid
  -> if repository/context drift is significant:
        movement via evidence/clarification may return to Explore/Model
  -> resume
```

Do not assume `current_mode` remains correct merely because it was persisted.

---

## 8. End of life

| Terminal status | Meaning |
|---|---|
| `closed` | Cycle completed under Workflow closure rules |
| `cancelled` | Cycle abandoned without claiming completion |

Optional archival of historical snapshots is allowed.  
Archived snapshots are not live Engineering State.

Live state = not `closed` and not `cancelled`.

---

## Lifecycle execution

```text
Engineer Cycle Intent
  -> Interpretation (create or restore state)
  -> Engineering State
  -> Operation selection coherent with current_mode
  -> Execution
  -> State update (mode / status / questions / artifacts)
  -> Workflow closure check
```

The integration:

- creates, updates, persists, restores, and ends state,
- does not redefine state fields or lifecycle semantics,
- maps tool mechanics onto this Core lifecycle.

See integration `OPERATING_MODEL.md` for tool-specific materialization.

## Non-goals

This document does not:

- redefine Mode meaning (`02.5`),
- redefine state fields (`02.6`),
- specify storage technology,
- define prompts/commands,
- replace Workflow closure authority.

## Evolution

Lifecycle changes require:

1. explicit Engineer approval,
2. demonstrated need from real multi-session / multi-tool cycles,
3. no contradiction with `02.5`, `02.6`, Principles, or Workflow.

### Future architectural note

This document currently describes lifecycle in terms of Engineering State.

A possible future refinement is to elevate **Engineering Cycle** as the primary concept:

```text
Engineering Cycle
    ├── Engineering State
    └── Lifecycle
```

In that framing, State remains the live representation, while Lifecycle describes the behavior of the cycle itself.  
This is noted for future evolution only. No structural change is required now.
