# JES — Engineering Cognition

> **Engineers do not follow phases. They navigate intentions.**
>
> This is the central claim of Engineering Cognition.
>
> Engineering Cognition is **not** a methodology, a workflow, a state-machine implementation, or an operation catalog.  
> It is the conceptual model describing how engineers navigate engineering work through changing intentions.
>
> It sits between architecture and process: it explains how engineering movement happens before workflow decides when work is complete.

---

## Central thesis

Most engineering methodologies describe ordered phases.

That description is useful for closure. It is incomplete as a description of how engineers actually work.

Real engineering work is navigational:

- new evidence changes intention,
- intention changes what artifact should be produced,
- artifact quality determines whether the engineer may move again.

JES therefore separates:

| Layer | Answers |
|---|---|
| **Principles** | Why do we decide this way? |
| **Engineering Cognition** | How does the engineer navigate mentally? |
| **Workflow** | When may the work be considered closed? |
| **Operations** | What executable actions materialize that work? |

This separation is independent of any tool.

---

## What Engineering Cognition is

**Engineering Cognition** is the model of how an engineer navigates a problem through distinct work intentions.

It answers:

> *What work intention am I in right now?*

It does not answer:

- what values govern decisions (Principles),
- how the system is layered (Architecture),
- when a change is complete (Workflow),
- what executable action to run (Operations).

### What it is not

Engineering Cognition is not:

- a replacement for Workflow,
- a checklist of mandatory steps,
- a prompt framework,
- an AI behavior policy,
- a project-management method,
- a catalog of tool commands.

It names a human engineering pattern that remains valid even if every AI tool disappears.

---

## Movement

**Movement** is the transition between work intentions caused by new evidence, decisions, constraints, or objectives.

An engineer does not change mode because a sequence “says so.”

An engineer changes mode because something changed in understanding:

- evidence contradicts a prior assumption,
- alternatives become clear enough to choose,
- a decision becomes stable enough to plan,
- an implementation becomes complete enough to validate,
- validation reveals that the model was wrong.

Movement is therefore evidence-driven.

This is why Engineering Cognition is better understood as a navigable graph than as a rigid pipeline.

---

## Why it exists

Without an explicit cognitive model, tools and agents tend to collapse all work into “do the task.”

That produces common failures:

- implementing before understanding,
- generating alternatives without closing a decision,
- treating documentation as a separate chore instead of persistent communication,
- confusing exploration with design, or design with decision.

Engineering Cognition exists to make intention explicit before execution begins.

Belonging criterion:

> If this concept would still matter after every AI tool disappears, it belongs to JES Core.

Engineering Cognition passes that test. It describes human engineering practice, not tool behavior.

## Relationship with Workflow

Workflow and Cognition are complementary.

| | Workflow | Engineering Cognition |
|---|---|---|
| Nature | Normative cycle | Navigable cognitive model |
| Question | When is work complete? | What intention am I in? |
| Shape | Phases with roles and exit criteria | Modes with artifacts |
| Authority | Closure and validation gates | Movement and framing of work |

One sentence:

> **Workflow governs closure. Cognition describes movement.**

### Refinement, not contradiction

Workflow phases may be coarser than cognitive modes.

Example:

```text
Workflow: Design
   contains
Cognition: Design -> Decide
```

Workflow `Design` remains the normative phase where the Engineer owns solution direction.  
Cognition refines that phase into:

- producing alternatives,
- then closing a decision.

This is a refinement of understanding, not a rewrite of `03_WORKFLOW.md`.

### Cycle Intent vs Mode

- **Cycle Intent** (Workflow): the objective of an engineering cycle (“what problem are we solving?”).
- **Mode** (Cognition): a named posture that represents a distinct engineering intention (“Explore”, “Decide”, “Build”).

A mode is not the intention itself.  
A mode **represents** an intention.

Example:

- intention: understand the system  
- mode: Explore  
- artifact: Understanding

Do not collapse Cycle Intent and Mode.

---

## Problem it solves

Engineering Cognition solves the problem of **unscoped action**.

It gives Engineer and Engineering Agent a shared language to:

1. identify the current intention before acting,
2. know what artifact that intention should produce,
3. know what that intention must not do,
4. move when evidence requires it — including backward.

It also explains why real work is not always linear:

- a small bug may move Explore → Build → Validate,
- an architectural change may loop Explore ↔ Model ↔ Design ↔ Decide many times before Build.

---

## What it does not solve

Engineering Cognition does not:

- replace Principles,
- replace Workflow closure rules,
- define tool commands or prompts,
- grant decision authority to AI,
- require every cycle to visit every mode,
- treat documentation as an independent cognitive mode,
- prescribe a mandatory transition table between modes.

---

## Governance (permanent constraint)

Governance is not a Mode.

It is a permanent constraint over all modes, in the same family as Principles:

- preserve human authority,
- keep scope bounded,
- require clarification when context is insufficient,
- maintain coherence across code, tests, docs, contracts, and workflow,
- refuse silent expansion of work.

Governance does not produce a primary work artifact. It conditions every mode and every movement.

---

## Cognitive behaviors (transversal)

These are not modes. They are qualities of movement inside every mode:

| Behavior | Role |
|---|---|
| **Reason** | Justify conclusions and tradeoffs |
| **Synthesize** | Reduce complexity to the useful core claim |
| **Communicate** | Make understanding transferable and persistent |

### Documentation as consequence

Documentation is not a cognitive mode.

It is a persistent manifestation of **Communicate** across modes:

- Explore → explanation
- Design → alternatives / ADR material
- Decide → recorded decision
- Build → change summary
- Validate → evidence
- Evolve → improvement proposal

Workflow still owns documentation as a closure concern. Cognition explains why documentation appears throughout the cycle.

---

## Modes

A **Mode** represents a distinct engineering intention.  
Each mode has a characteristic question and a characteristic artifact.

The preferred reference path is:

```text
Explore -> Model -> Design -> Decide -> Plan -> Build -> Validate -> Evolve
```

This path is a guide, not a rigid pipeline.

Real work is a **navigable directed graph**: evidence can send the engineer back to earlier modes (especially from Validate).

### Mode catalog

| Mode | Intention | Question | Produces |
|---|---|---|---|
| **Explore** | Understand | What exists and how does it work? | Understanding |
| **Model** | Structure the domain | What is the domain world? | Mental Model |
| **Design** | Generate options | What options are viable? | Alternatives |
| **Decide** | Close direction | What do we choose? | Decision |
| **Plan** | Organize execution | How will we execute? | Execution Plan |
| **Build** | Change the system | What do we change? | Change |
| **Validate** | Verify readiness | Is it correct and ready? | Evidence |
| **Evolve** | Improve over time | How should the system improve? | Improvements |

### Mode boundaries (non-goals)

- **Explore** does not change the system.
- **Model** does not select a solution; it defines the world in which solutions make sense.
- **Design** does not close the choice; it produces alternatives and tradeoffs.
- **Decide** does not implement; it closes direction under Engineer authority.
- **Plan** does not redesign; it turns an approved decision into verifiable execution.
- **Build** does not redefine architecture by stealth.
- **Validate** does not invent new scope; it checks against criteria.
- **Evolve** is not a local refactor task; it is longitudinal system improvement.

These boundaries protect the model from collapsing back into undifferentiated “do work.”

### Navigability

Modes may be skipped when evidence already exists.  
Modes may be revisited when validation (or new understanding) invalidates prior assumptions.

Movement is governed by evidence, not by obligation to complete a sequence.

Example loop observed in practice:

```text
Validate
  -> "this concept does not belong here"
  -> Model
  -> Design
  -> Decide
  -> Build
  -> Validate
```

## Relationship with Engineering State

Engineering Cognition defines Mode meaning.  
The live cycle instance is carried by **Engineering State**.

See `02.6_ENGINEERING_STATE.md`.

```text
Cognition (meaning)
    |
    v
Engineering State (live instance: current_mode, triggers, status, ...)
    |
    v
State Lifecycle (create / evolve / persist / end)
    |
    v
Operations / Workflow (consume state)
```

See also `02.7_ENGINEERING_STATE_LIFECYCLE.md`.

Operations consult Engineering State during execution.  
They do not re-interpret Cognition ad hoc on every step.

---

## Relationship with Operations

Engineering Operations are executable units that materialize cognitive movement under Engineering State constraints.

```text
Cycle Intent
    |
    v
Mode navigation (recorded in Engineering State)
    |
    v
Engineering Operation(s)
    |
    v
Workflow phase progress and closure
```

Rules:

- one Mode may map to one or more Operations,
- Operations must not redefine Cognition,
- Integrations implement Operations; they do not invent cognitive meaning.

The operation catalog remains in `08_ENGINEERING_OPERATIONS.md` and stays frozen until Cognition-driven revision is explicitly approved.

---

## Practical use

Before acting, Engineer or Engineering Agent should be able to answer:

1. What is the Cycle Intent?
2. Which Mode are we in?
3. What artifact must this mode produce?
4. What must this mode not do?
5. Which Workflow closure concerns are still open?

If those answers are unclear, Governance requires clarification before Build.

---

## Evolution of this document

This document captures a foundational concept discovered by naming existing engineering practice.

Changes to Engineering Cognition require:

1. explicit Engineer approval,
2. demonstrated value across more than one project context,
3. no contradiction with Principles.

Mode details may refine over time. The core separation — Cognition as movement, Workflow as closure, Operations as execution — should remain stable.

Future refinements may include an explicit account of common evidence-driven transitions between modes. That section is intentionally deferred until the core concept has remained stable in use.
